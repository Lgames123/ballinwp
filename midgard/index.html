Security proposal · MidgardSurvivors 0.1.276

Move progression to the server and make every save online-only

Today the game client owns the save file, computes its own rewards and posts its own records. This proposal moves all three behind an authenticated API, using the run-ticket model Pokébonk already runs in production, adapted to the Supabase project MidgardSurvivors already uses.

Audience: MidgardSurvivors developer Scope: profile, economy, runs, leaderboards, patches Stack: Godot 4 client · Supabase (Auth, Postgres, Edge Functions)

Summary

The short version

Problem

Every trust decision happens on the player's machine. The save key, patch key and API key all ship inside the .pck, so saves, cloud uploads and leaderboard posts can be forged with a text editor and one HTTP call.

Proposal

The server owns the profile. The client asks for a run ticket, sends checkpoints while playing, and sends a result at the end. The server validates it, grants rewards and writes the leaderboard. Spending is done through server commands.

Cost

One Edge Function, ~10 tables, one new Godot autoload, and changes at the places that write Save today. No change to combat code, no extra latency during a run. Six phases that ship independently.

What "server authoritative" means here. Combat keeps running on the client, as it does in Pokébonk. The server becomes authoritative over everything that persists: currencies, cards, equipment, unlocks, class levels, records and rankings. Combat results are validated against server-side rules and the server's own copy of the loadout instead of being trusted. Full server re-simulation is out of scope, because the simulation is not deterministic (identical seeds still vary by about 5–7% between bench runs).

Where things stand

Current trust model, from the shipped build

Paths use the project layout (scripts/autoload, scripts/core). Line numbers come from the 0.1.276 build and may be a few lines off from the editor sources. Key values are intentionally not reproduced here.

F1
Critical

The save file is the source of truth, and the client holds its key

Save.flush() writes user://profile.json with open_encrypted_with_pass(…, SAVE_KEY), and SAVE_KEY is a string constant. Anyone who unpacks the .pck can decrypt, edit (zeny, cards, refines, class stats, tower builds) and re-encrypt the profile, and the game accepts the result as real progress.

Critical

Cloud save stores whatever the client uploads

CloudSave.pack() AES-encrypts the profile with a key derived from the same SAVE_KEY, and cloud_put stores the blob. The server cannot read or check it, so an edited local save becomes the cloud save on the next sync. The conflict dialog's "use this device" button calls _push(-1), which overwrites the cloud copy without a revision check.

Leaderboard writes are unauthenticated

The player's identity is player_id, 12 random bytes kept in the save settings. submit_record, submit_festival, submit_tower and rename_player are Supabase RPCs called with the publishable key and that id, and they accept the score as a parameter. Anyone can post any score, for any class, under any id, without running the game.

Reference

What Pokébonk does, and what to copy

Pokébonk is a browser survivors-like with the same problem: the simulation runs in the client. Everything below is visible in its public client bundle and API responses.

Accounts before anything else

  • Guest accounts are created server-side (POST /auth/guest) behind a Cloudflare Turnstile check, then upgraded to a named account with the same id (/auth/upgrade).
  • Every call carries Authorization: Bearer, a per-install X-Device id and the X-Client version.
  • The server answers 426 for outdated clients, 403 {banned} for bans and 503 {maintenance} during deploys.
main-*.js · req(), guest(), register(), upgradeGuest()

The profile lives on the server

  • GET /profile returns the full profile plus the server's now, which the client uses to measure clock skew.
  • The only thing the client may write directly is PUT /profile/prefs, a whitelist of cosmetic fields (settings, avatar, team, skins).
loadProfile(), savePrefs()

Spending is a command

  • Each purchase is its own endpoint: /lab/buy, /items/buy, /shop/buy, /quests/claim, /tasks/claim, /treasures/spin.
  • Smaller toggles are batched into POST /profile/actions. Every response returns the new profile.
buyLab(), buyShop(), claimTask(), actions()

Runs are tickets

  • POST /runs with a client idempotency key returns {id, seed, ranked, targets}. Retries reuse the key.
  • If the server cannot be reached after three tries, the run is local, unranked and "progress is not saved".
startRun() → {id:'', ranked:false, offline:true}

Heartbeat checkpoints

  • Every 60 s of game time, and on boss kills, stage changes and tower floors, the client queues {t, stage, kills, level, damage, splits}.
  • Queued checkpoints are posted in batches of up to 300 to /runs/:id/checkpoint.
checkpoint(), flushCps(), heartbeat:60

Finish, with a durable queue

  • POST /runs/:id/finish {result, cps} returns the rewards and the updated profile. The server computes rewards; the client never sends a currency amount.
  • The result is stored locally first (pb.pending) and resent with exponential backoff. 409 means "already saved" and counts as success.
finishRun(), flushPending(), retryLater()

Pause and continue anywhere

  • /runs/:id/save stores a gzip snapshot with a hash. /suspend, /resume and /recover move a run between devices.
  • A browser lock and a heartbeat in local storage stop the same run from being played in two tabs.
uploadSave(), suspendRun(), resumeRun()

Server-side rules and bans

  • Rules include speed, kill-impossible, burst, level-impossible, gold-impossible, checkpoints-missing, counters-forged, result-forged and result-repeat.
  • Two flagged runs in 7 days trigger a 30-day ban. Podium runs (top 3 per map, top 10 global) get extra review. Device farms and parallel runs are tracked.
autoBan {runs:2, days:7, ban:30}, podium, deviceFarm

Do not copy Pokébonk's mistake: its thresholds ship to the client. The full rule table (heartbeat, maxGap, killSlack, burstPerSec, autoBan …) sits in a shared module of the public bundle. Third-party tools can read it and keep every value just under each limit, for example by reporting a movement speed slightly below the speed rule while the real one is higher. In MidgardSurvivors the rule values must live only in the Edge Function, and the client should receive nothing more specific than "rejected".

functions/api/index.ts
async function finish(c: Ctx, runId: string, body: { result; cps? }) {
  const { data: run } = await db.from("runs").select("*").eq("id", runId).single();
  if (!run || run.account_id !== c.uid) return json(404, { error: "run" });
  if (run.status === "finished") return json(409, { error: "already_saved", rewards: run.rewards });

  const verdict = await validateRun(db, { run, checkpoints, result: body.result, now: c.now });
  if (verdict.reject) return json(422, { error: "rejected" });   // never say which rule fired

  // Rewards come from validated, clamped telemetry. No client field is copied into the profile.
  const rewards = computeRewards(state, run, body.result, verdict);
  const rev = await commit(c.uid, p.rev, state, "run", runId, rewards.delta);
  if (verdict.ranked) await writeBoards(c.uid, run, body.result, verdict);
  return json(200, { rewards: rewards.delta, profile: state, rev });
}

Festival: a rule that uses the game's own numbers

Emperium k spawns with max_hp = FESTIVAL_BASE_HP × FESTIVAL_GROWk (festival_run.gd:396, constants at game_data.gd:176–177: 6000 and 1.4). Breaking n of them therefore needs a known minimum of banked damage, and the 60 s window (FESTIVAL_TIME) gives a minimum sustained DPS.

min_damage(n) = 6000 × (1.4n − 1) / 0.4
n = 100 → 6.2 × 1018  ·  n = 131 → 2.1 × 1023  ·  n = 147 → 4.5 × 1025 (≈ 7.6 × 1023 DPS over 60 s)
  • The client sends a checkpoint at each break (festival_run.gd:417 checks += 1) with the banked damage. Fewer logged breaks than claimed checks is a reject.
  • The time between breaks gives a DPS curve. A legitimate build ramps smoothly; an injected score jumps.
  • Send damage as a float or as log10, not through big(), so top entries stop collapsing to the 9×1018 cap (F9).
  • Podium entries (top 3 per class, top 10 overall) go to pending_review before they appear on the public board, as Pokébonk does with its podium rule.
functions/api/validator.ts
function festival(ctx: RunContext, add) {
  const n = Number(ctx.result.checks ?? 0);
  const banked = Number(ctx.result.dmg ?? 0);
  const minDmg = (GD.FESTIVAL_BASE_HP * (Math.pow(GD.FESTIVAL_GROW, n) - 1)) / (GD.FESTIVAL_GROW - 1);
  if (banked + 1 < minDmg * 0.999) add("result-forged", "reject", { n, banked, minDmg });

  const breaks = ctx.checkpoints.filter((c) => c.payload.kind === "check");
  if (breaks.length < n) add("checkpoints-missing", "reject", { logged: breaks.length, claimed: n });
  // ... DPS between consecutive breaks, window length ≤ FESTIVAL_TIME + 2 s
}

Delivery

Roadmap

Each phase ships on its own and leaves the game playable. Phases 0–2 already stop the cheapest attacks.

0Quick hardening

Close the open doors

  1. Remove the client_unsafe() TLS fallback in Leaderboard._call (F7).
  2. Sign the patch manifest and every .pck with a private key kept off the build machine; verify with an embedded public key before _decrypt (F8). Crypto.verify is already used by Save.dev_verify.
  3. Add a server-side minimum version: every RPC compares p_version and refuses older clients.
  4. Clamp obviously impossible values inside the existing submit_* SQL functions (score ceilings per class and stage) while the rest is built.

Done when a proxy with a self-signed certificate gets no traffic, and an unsigned patch is refused.

1Accounts

Real identity on every request

  1. Enable Supabase anonymous sign-ins. First launch creates an anonymous user; the existing register/login/security-questions flow upgrades it to a named one with the same id.
  2. Add the Api autoload (api.gd) with session refresh, X-Device and X-Client headers.
  3. Create accounts; store the old player_id and cloud_user in legacy_* columns at first login so old board rows stay attached to their owner.
  4. Optional: link the Epic account the game already initializes through EOS, so a name cannot be taken twice.

Done when every call carries a JWT and no RPC uses p_player or p_secret as proof of identity.

2Server profile

The profile moves to Postgres

  1. Create profiles and ledger; deploy GET /profile and POST /profile/actions.
  2. Port the pricing and rules behind spend, fuse_card, set_eternal, unlock_class, set_class_stats, toggle_pact, claim_achievement into actions.ts, reading the same GameData tables (export them to JSON at build time so client and server never drift).
  3. Turn Save.data into a read-only cache that adopts the server profile (save_and_world_changes.gd). flush() keeps device settings only.
  4. Retire cloud_put / cloud_get and the conflict dialog; there is one copy now.

Done when editing profile.json changes nothing after a restart.

3Run tickets

Runs start and end on the server

  1. Deploy /runs, /checkpoint, /finish, /snapshot, /suspend, /resume.
  2. World.start_run requests a ticket and builds the hero from the returned loadout; the run RNG is seeded from ticket.seed.
  3. Add the 60 s heartbeat and event checkpoints (boss kill, stage change, tower floor, Emperium break).
  4. _end_run / _bank_run stop writing Save; computeRewards on the server mirrors add_class_xp, ore and zeny rules, and DAILY_FIRST_BONUS.
  5. Boards are written only inside /finish. Revoke submit_record, submit_tower, submit_festival for the anon role.

Done when a direct RPC call cannot create a board row and a run without a ticket grants nothing.

4Validation

Rules, review queue, enforcement

  1. Ship validator.ts with every rule at review. Calibrate thresholds from log_run_metrics history (p99.9 per class, stage and danger).
  2. Build a small admin page over flags (confirm / clear) and the podium pending_review queue.
  3. Promote rules to reject once false positives are below an agreed rate; enable shadow flags, then bans with human confirmation.

Done when the top of every board has been reviewed and the flag queue is worked weekly.

5Cutover

Import old saves, then go online-only

  1. Ship a client that uploads the local profile once to POST /migrate (see the next section).
  2. Raise MIN_CLIENT so older builds receive 426.
  3. Remove the local progression code paths and the SAVE_KEY-encrypted profile file. Offline play becomes practice mode.
  4. Archive the old boards as "Legacy season" and start a fresh, validated season.

Done when no supported client can change progression without the API.

6Optional

Loot tickets and replays

  1. Loot tickets: the server pre-rolls rare drops for each checkpoint window with an HMAC of run_secrets.loot_key and sends signed tokens. The client may only claim drops it was issued, so card and MVP-drop farming through memory edits stops working.
  2. Replays for the podium: record seed plus inputs for top runs only, and add a deterministic mode (fixed timestep, seeded RNG everywhere) so a reviewer can watch the run.

Delivery

What changes for players

Better than today

  • One save, on every device. The "which save do you keep?" dialog (cloud_save.gd:471) disappears.
  • Quit mid-run on PC, continue on the web build.
  • Leaderboards that players can believe.
  • Lost device or reinstall: log in, everything is there.

Costs to soften

  • No connection at start: the run is a practice run, with a clear banner that it grants nothing.
  • Connection lost mid-run: the run continues; checkpoints and the finish wait in the queue and send when the connection returns (48 h grace).
  • Server maintenance: menus open read-only from the cache, with the maintenance message from 503.
  • Commands in menus wait for a round trip; show the new value only after the response.
Delivery

Co-op runs

  • Co-op stays peer-to-peer over EOS with the host simulating (net_sync.gd:247 is_host, :854 host_tick). The server does not need to see gameplay traffic.
  • The host creates a party_id; every member requests their own ticket with it, so each member's loadout comes from their own server profile.
  • Each member sends checkpoints and a finish. The validator compares them: shared counters (time, kills, stage, Emperium breaks) must agree within a small tolerance, and the party board row is written only when the members agree.
  • Co-op is the one place where RunSave is already disabled (run_save.gd:44), so suspend/resume stays solo-only.
Delivery

Trade-offs and limits

TopicAssessment
Server costAbout 3 requests at start and end, plus 1 per minute of play. A 30-minute run is ~35 small requests. Edge Functions and Postgres on the current Supabase plan handle this volume without changes.
LatencyNone in combat. Menus wait one round trip per purchase.
What it does not stopA modified client can still play better than a human inside plausible limits (auto-aim, auto-pick). Validation narrows the window; podium review and replays (phase 6) cover the top of the boards, where it matters.
False positivesReal builds reach extreme numbers (Festival entries above 1025 damage are legitimate). Rules must be relative to stage, danger and loadout, start at review, and bans need a human.
Balance patchesRules that use game constants must read them from the same exported GameData JSON the server uses for prices, versioned with the client.
PrivacyStores an account id, an optional name, a random device id and gameplay data. No email is required.

func start_run(opts: Dictionary) -> Dictionary:
	var key := Crypto.new().generate_random_bytes(8).hex_encode() + str(Time.get_ticks_msec())
	for attempt in 3:
		var r := await req('/runs', HTTPClient.METHOD_POST, opts.merged({'key': key}))
		if r.ok:
			_ticket = r.data          # {id, seed, loadout, ranked}
			return r
		if not r.offline:
			return r
		await get_tree().create_timer((0.5 + randf() * 1.5) * (attempt + 1)).timeout
	# Online-only: no ticket means a practice run that grants nothing.
	_ticket = {}
	return {'ok': false, 'offline': true, 'practice': true}
